# confirm-gate 面试速查

> 一页纸。被问到时按这个顺序讲。

## 30 秒版本

> 我在 DeepSeek Harness 上写了一个插件。
>
> 起因是 Windows 沙箱会让 `pwsh` 工具全部崩掉（`0xC0000142`），用户被迫开完全权限——
> 这时 agent 可以无限试错、乱改文件，没人记账。
>
> 我做的是**每轮对话的持久化操作计数器**：额度内提醒，超了发停止指令，
> 到硬上限索要确认。它不是安全边界，是成本边界。
>
> 一天完成，716 行，27 项测试全过，真机验证了三种权限模式的实时切换。

## 3 分钟版本（按这个展开）

**1. 定位（10 秒）**
不是沙箱，不做拦截。沙箱解决「不许做」，我做「做太多」。
这两件事不能互相替代——尤其当沙箱不可用时，后者才是唯一能做的。

**2. 机制（30 秒）**
挂在 `tools/pre-execute` 上，三档：提醒 → 停止指令 → 索要确认。
关键设计有两个：
- **非持久化操作永不计数**（读、搜、列目录），否则会打断正常思考
- **命令级判定**：`pwsh` 不按工具名算，看命令内容，`Get-ChildItem` 不消耗额度

**3. 最难的一个 bug（60 秒）**
插件加载了、钩子注册了、每次调用都触发了，**但不计数**。
根因三叠：cordis 懒注入导致 `ctx.shell` 抛错 → catch 吞掉 → 我把「读不到」当成「不安全」选了沉默。
用三层探针（模块加载 / 初始化 / 钩子触发）才定位。
这件事改变了我对「保守」的理解：**对记账工具，静默比吵闹危险**。
所以我改成了 fail open——读不到就照常工作，宁可多提醒。

**4. 验证（30 秒）**
27 项离线测试 + 真机热切换。
最关键的一条证据是：切到沙盒再切回完全权限，**同一进程内**门控恢复计数。
这证明「按次判定」优于「加载时判定」。

**5. 诚实的地方（20 秒）**
README 里明确写了两处限制：
- 当前部署 `ctx.get('shell')` 返回 undefined，行为正确但走的是兜底分支
- 花费 0.27 USD 是估算不是账单，口径写清楚了

**6. 产出（20 秒）**
GitHub 开源，MIT，双语 README，35 KB 成品包挂在 Release 上。

## 可能被追问的五个问题

**Q：为什么不做语法解析？**
A：插件跑在 DSH 进程内，是 ESM 模块，调不到 PowerShell 的 AST 解析器。
只能提取命令名做集合比对。错的方向是多计一次，不是漏拦——这是有意选的。

**Q：fail open 会不会不安全？**
A：它不是安全边界，所以不存在「不安全」这个问题。
两害相权：多提醒看得见改得掉，静默失效没人知道。安全边界才该 fail closed。

**Q：为什么 confirm 放行整轮？**
A：confirm 是对一件事的授权，不是对一次操作的授权。
按笔确认会把一次执行切成十次中断。代价是粗粒度，讨论时提到 confirm 也会触发，
我选了简单规则——把歧义交给用户措辞，而不是让插件猜意图。

**Q：怎么保证测试可信？**
A：两条。一，`file:` 安装是复制，存在两份文件，我用 hash 比对确认测的是新代码。
二，假 ctx 必须模拟真实形状——我用过太简单的假对象，测试全过真机全挂。

**Q：这个插件最有价值的发现是什么？**
A：`ctx.shell.sandboxMode` 是默认值，不跟热切换变。
官方注释里就写着 "applies by default"，但很容易被当成当前值。
这条不问不查，热切换永远修不好。
